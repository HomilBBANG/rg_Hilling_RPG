# 다이얼로그 노드 에디터 — Claude Code 개발 핸드오프 v10.5

> **사용자 확정:** 대사량이 많은 힐링 RPG를 위해 **전용 다이얼로그 편집기 자체를 개발해야 한다.**
> **아래의 UI 형태/구현 기술은 제안 및 개발용 초기안:** 노드형 UI, Godot `EditorPlugin` + `GraphEdit`/`GraphNode`, 데이터 포맷, 단축키와 미리보기 형식은 아직 사용자 승인 전이다. 확정되지 않은 대화 중 시간 정지·컷씬 스킵 규칙을 임의로 만들지 않는다.
> **제작 주체:** Claude Code가 기존 Godot 프로젝트에 통합. 대사 및 퀘스트 기획자가 코드를 고치지 않고 콘텐츠를 추가할 수 있도록 만들 것.

## 1. 핵심 목표

- NPC 수십 명과 여러 장소·퀘스트에서 등장하는 대사를 **에디터에서 검색/작성/연결/테스트/저장**할 수 있어야 한다.
- **대화 노드(콘텐츠)**와 **게임의 대화 실행기(런타임)**를 분리하고, 하나의 데이터가 에디터 미리보기와 실제 Godot 플레이에 모두 사용되게 한다.
- 기본 선형 대화, 선택지 분기, 월드/퀘스트 조건 판정, 퀘스트 진행 이벤트, 컷씬 호출을 코드 편집 없이 연결한다.
- 왕의 용 토벌 → 첫 동행 고양이 → 용 토벌 → 캠핑카 소원이라는 확정된 이야기 순서를 침해하지 않는다.
- 시각 스타일(P0 검증) 및 게임 시스템 개발을 중단하고 전체 서사 에디터를 완성하려 하지 말 것. **대사 1개를 제작→미리보기→실게임 실행하는 가장 작은 흐름을 먼저 검증**할 것.

## 2. 편집기 형식 — 우선 권고

### Godot 내장 에디터 플러그인 [제안]

- `@tool` + `EditorPlugin`으로 Godot 에디터 안에 **Dialogue Editor** 패널을 제공한다.
- 중앙은 `GraphEdit`/`GraphNode`를 사용한 연결형 그래프, 왼쪽은 대화 목록·검색·새 대화 생성, 오른쪽은 선택 노드의 속성 편집, 아래는 미리보기와 오류 패널로 구성한다.
- **노드 텍스트를 작은 박스에 억지로 여러 줄 편집하지 않는다.** 그래프 노드에는 이름/대사 미리보기 1~2줄만 표시하고, 전체 문장 편집은 오른쪽 속성 패널에서 수행한다.
- 노드 이름/대화 제목은 선택 후 바로 편집할 수 있게 하고, 키보드 입력/복사 붙여넣기를 편하게 구현한다.
- 여러 대화 파일을 열거나 NPC·퀘스트·지역별 대화를 찾을 수 있도록 `dialogue_id`, `speaker_id`, `tags`를 저장한다.
- 나중에 외부 웹 편집기로 전환할 수 있도록 **직렬화 포맷과 런타임 로직은 EditorPlugin에 종속되지 않게 한다.**

## 3. 노드 종류 (최소 7종) [구현 제안]

| 노드 | 기능 | 주요 속성 |
|---|---|---|
| `Start` | 진입점, 그래프당 하나 | `next` |
| `Line` | NPC/플레이어의 단일 대사 | `speaker_id`, `text`, `next` |
| `Choice` | 선택지별 다른 연결 | 선택지 `label`, `next`, 선택지별 표시 조건(선택) |
| `Condition` | 상태를 검사해 두 갈래 이상 분기 | 조건 키, 연산자, 참/거짓 링크 |
| `Action` | 퀘스트/월드 플래그 등 상태 변경 호출 | 허용 명령 타입, 인자, `next` |
| `CutsceneCall` | 별도 컷씬 이벤트를 호출 | `cutscene_id`, `next` |
| `End` | 종료하고 플레이어 조작 반환 | 완료 기록 여부 등 |

**`Action` 노드의 허용 명령은 제한된 목록만 제공한다.** 첫 버전은 `set_flag`, `quest_accept`, `quest_advance`, `mark_event_complete` 등 기존 매니저가 지원하는 것만 연결한다. 새로운 보상 규칙이나 임의의 코드 실행을 도입하지 않는다. `give_item`, 호감도 변경, 카메라/애니메이션 제어는 기존 시스템/API가 확인되면 후속 확장한다.

**분기 규칙:** 조건은 `get_flag`, 퀘스트 상태 등 기존 조회 API만 사용한다. 원문 대사·사용자 입력을 코드로 `eval`/`Expression.execute`하지 않는다. 연결 없는 분기는 저장 전 오류로 표시한다.

## 4. 공통 데이터와 연동 [제안]

- 각 대화는 사람이 읽을 수 있는 **고유 ID**를 가진다. 예: `dialogue.king.dragon_offer`, `dialogue.npc.shopkeeper.hello`.
- 노드는 파일 내에서 안정적인 **고유 노드 ID**를 가진다. 표시 이름을 바꾸거나 위치를 움직여도 연결이 끊어지지 않게 한다.
- 대화 내용과 그래프 좌표를 외부 데이터로 저장한다. 현재 프로젝트의 `.tres` 파이프라인이 적합하면 유지하고, 아니라면 **버전이 명시된 UTF-8 JSON**(`res://data/dialogues/*.json`)을 권장한다. 아래 예제는 JSON 형식이다.
- `version`, `dialogue_id`, `metadata`, `start_node_id`, `nodes`, `connections`, `editor_positions` 필드를 권장한다.
- `speaker_id`와 실제 NPC 오브젝트 연결은 별도의 등록 정보/기존 NPC 시스템을 통해 처리한다. NPC마다 대본 내용을 GDScript에 직접 작성하지 않는다.
- 런타임에서 `DialogueRunner.play(dialogue_id, context)` 식으로 호출한다. 구체 API 이름은 기존 코드에 맞게 결정한다.
- 에디터는 **게임 저장 파일을 수정하지 않는다.** 에디터의 미리보기에서는 테스트용 플래그/퀘스트 상태를 복제해 이용하며 실게임 진행 데이터에 영향을 주지 않는다.
- 이벤트 보상·퀘스트 수락은 **여러 번 재생하더라도 중복 적용되지 않도록 기존 NarrativeState/QuestManager의 완료 플래그**를 사용한다.

### 간단한 샘플 데이터 [모든 텍스트는 테스트용이며 정식 스토리 미확정]

```json
{
  "version": 1,
  "dialogue_id": "dialogue.demo.dragon_offer",
  "metadata": {"title": "왕의 의뢰 테스트", "tags": ["tutorial", "quest"]},
  "start_node_id": "start",
  "nodes": [
    {"id": "start", "type": "start"},
    {"id": "line_01", "type": "line", "speaker_id": "king", "text": "여행자여, 부탁할 일이 있다."},
    {"id": "choice_01", "type": "choice", "options": [
      {"port": "accept", "text": "의뢰를 수락한다."},
      {"port": "later", "text": "나중에 듣겠다."}
    ]},
    {"id": "accept", "type": "action", "action": "quest_accept", "args": {"quest_id": "quest.dragon"}},
    {"id": "end", "type": "end"}
  ],
  "connections": [
    {"from": "start", "port": "next", "to": "line_01"},
    {"from": "line_01", "port": "next", "to": "choice_01"},
    {"from": "choice_01", "port": "accept", "to": "accept"},
    {"from": "choice_01", "port": "later", "to": "end"},
    {"from": "accept", "port": "next", "to": "end"}
  ],
  "editor_positions": {}
}
```

- 예시는 **데이터 계약 검증용**으로만 사용. 왕 대사·선택지·의뢰 수락 방식 및 UI는 GDD에서 아직 확정하지 않았다.
- 실제 파일 스키마는 한 가지로 통일하고 검증기와 런타임이 같은 규칙을 공유하도록 하라.

## 5. 사용자가 실제로 해야 할 작업 흐름

1. Godot를 열고 `Dialogue Editor` 패널을 클릭한다.
2. `새 대화`를 만들거나 NPC 이름·태그·퀘스트 ID로 기존 대화를 검색해서 연다.
3. 캔버스에서 `Line`, `Choice`, `Condition` 등을 추가하고 선으로 연결한다.
4. 속성 패널에 화자/대사/조건/액션을 입력한다. 복사·붙여넣기와 텍스트 줄바꿈을 지원한다.
5. **미리보기**를 클릭해 실제 대화창으로 분기를 진행한다. 임시 플래그/퀘스트 값을 변경해 조건별 결과도 테스트한다.
6. **검증**을 클릭해 누락 연결·불가능한 분기·오타 ID 등을 검사한다.
7. **저장**하면 데이터 파일이 수정되고, 게임에서는 같은 `dialogue_id`로 내용을 불러온다.
8. NPC 씬 또는 이벤트 트리거에 해당 `dialogue_id`를 연결한다. 대사를 바꾸기 위해 NPC GDScript를 편집하지 않는다.

## 6. 편의 기능 및 오류 방지

### P1 필수 기능 [제안]

- 신규/열기/저장, 노드 생성·삭제·연결·이동·문장 수정
- `Line`, `Choice`, `Condition`, `Action`, `CutsceneCall`, `End` 실행 및 실행기 연동
- 미리보기: 선택지 조작, 테스트 플래그 조정, 현재 실행 노드 하이라이트
- 검증: 시작점 누락, 중복 노드 ID, 존재하지 않는 연결 대상, 연결 없는 선택지, 지원하지 않는 액션, 잘못된 퀘스트/컷씬 ID, 도달 불가 노드
- 저장 후 재실행해도 동일하게 로드되고 그래프 위치와 연결 상태 유지
- UTF-8 한글 대사/줄바꿈/긴 대사 정상 표시

### P2 품질 개선 [제안]

- `Ctrl+S`, 실행 취소/다시 실행, 복사·붙여넣기·다중 선택, 검색·필터, 노드 정렬
- NPC/퀘스트별 대화 수량 표시, 재사용 가능한 대화 호출, 조건 템플릿
- CSV/JSON 내보내기, 로컬라이제이션 키, 대사 텍스트 일괄 검색/치환
- 미리보기 중 액션 발생 기록, 시작 지점 선택 실행, 오류 위치 바로 가기
- 변경 전 데이터 백업·명시적인 저장 충돌 경고

**큰 원칙:** 기능을 한꺼번에 화려하게 구현하기보다, **복잡한 대사를 실제로 작성할 수 있는지**를 먼저 증명한다.

## 7. 컷씬 에디터와의 경계

- 첫 버전의 다이얼로그 에디터는 **컷씬을 호출하고 대사 순서를 연출에 연결**하는 데 집중한다.
- `CutsceneCall`의 대상 컷씬은 기존 `CutsceneRunner`의 단계 데이터로 재생한다.
- 풀 타임라인/키프레임 컷씬 편집기, 카메라 경로 에디터, 애니메이션 에셋 제작기는 **별도 후속 도구로 보류**한다. 현재 고정 탑다운 카메라·회전 금지 유지.
- 대화·컷씬·퀘스트 상태 갱신은 순차적 이벤트 실행기를 공유한다. 스킵/대화 중 게임 시간 정책은 미정이므로 구현 가정을 문서로 남긴다.

## 8. 개발 마일스톤 [제안]

**ED0 (기존 P0 그래픽 테스트를 막지 않는 선에서):**
- 최소 그래프 리소스의 생성/로드/저장과 기본 노드 캔버스, 대사 한 줄 미리보기.

**ED1 (많은 대사를 실제로 쓰기 위한 필수 단계):**
- 7종 노드, 연결형 분기, 실게임 대화 실행기 연동, 초보자도 코드 없이 편집.
- 왕의 대화 1개 + 일반 NPC 대화 1개 + 고양이 첫 등장 컷씬 호출 1개를 테스트 데이터로 연결.

**ED2 (콘텐츠 양이 늘기 전에):**
- 검색, 검사, 실행 취소, 키보드 단축키, 복사/붙여넣기, 미리보기 조건 조작, 폴더/태그 정리.

## 9. 검증 시나리오와 완료 기준

- 빈 Godot 프로젝트가 아니라 **기존 게임 프로젝트에서** 플러그인이 열린다.
- 비개발자도 NPC 대사를 추가·수정·분기하여 **GDScript 한 줄 변경 없이** 실게임에 반영한다.
- 선택지, 조건 분기, 퀘스트 플래그, 컷씬 호출이 동일한 실행기로 작동한다.
- 플레이 테스트에서 대화 종료 후 조작 및 카메라 상태 정상 복구.
- 대화 파일 저장 → 에디터 종료 → 재실행 → 연결과 문장 정확히 복원.
- 잘못된 연결/존재하지 않는 ID는 에디터 검증에서 찾을 수 있다.
- 일반적인 편집 과정에서 다른 게임 진행 데이터·세이브·퀘스트 보상이 바뀌지 않는다.
- 플러그인과 런타임을 명확하게 분리하고, 빌드에서 `EditorPlugin`을 요구하지 않는다.

## 10. Claude Code에 바로 전달할 명령

> 기존 Godot 프로젝트를 분석해 현재 NPC 대화, 퀘스트, 컷씬, NarrativeState, 저장 데이터 구조를 확인하라. `GDD.md`의 17장을 읽고 `DIALOGUE_EDITOR_HANDOFF.md`에 따라 **기획자가 대사와 분기를 작성할 수 있는 노드형 다이얼로그 에디터**를 우선 구현하라. Godot 4.x `EditorPlugin`/`GraphEdit` 방식은 권장안이며 기존 프로젝트와 맞지 않으면 이유를 보고하고 대안을 선택하라. 첫 단계에서 새 대화 작성·저장·불러오기·대사/선택지/조건/이벤트 연결·실게임 실행 및 미리보기·데이터 검증까지 하나의 작동하는 흐름을 만들라. 임시 대사는 정식 서사로 간주하지 말 것. 구체 구현 및 미정 정책은 `IMPLEMENTATION_ASSUMPTIONS.md`에 기록하고 기존 확정된 게임 로직/그래픽/카메라/퀘스트 규칙을 보존하라.
